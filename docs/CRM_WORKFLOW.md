# Customer profiles and staff CRM

Draft implementation verified locally on 19 October 2026. Per the latest user instruction, CRM activation is deferred until the website work is complete; preserve this draft without starting more CRM features or applying it remotely. The new profile migration has **not** been applied to a remote database, and this work does not establish that hosted authentication or production CRM is working.

## Customer workflow

After signing in, `/dashboard` shows the account's permanent customer reference and editable customer card. Customers choose Individual or Company, enter first name, last name, international mobile number and country of residence, and select one or more services: Concierge, Flights, Hotels, Transfers, Cruises or Travel bundles. Company accounts require a company name. Account email is read-only and synchronized from Supabase Auth; changing profile details cannot replace the customer reference or account ownership.

Saving updates the existing profile rather than creating another customer. Historical full names remain visible until the customer supplies first and last names separately; no automated name splitting is performed. Existing country text is retained as a selectable legacy value; new selections use ISO country codes.

The dashboard loads that customer's enquiries in pages of 100, with an explicit user filter before pagination and a stable created-time/ID ordering. Each enquiry can show its timestamped status history. Private staff notes and tasks are never requested by the customer history component. A Load older enquiries button retrieves subsequent pages without a fixed 500-record display cap.

## Staff workflow

`/admin` is available to administrators whose role is returned by the existing `user_roles` query. PostgreSQL permissions and RLS enforce access independently of the interface.

The customer directory includes registered accounts with no enquiry. Staff can search names, customer IDs, email, mobile, company and country, filter by account category or service, open a customer card and view that customer's enquiries. Enquiries can also be filtered by status. The directory and enquiry list each load 100 records per page, with separate Load more controls. Search and filters operate on the pages already loaded; the interface explains this when more records remain. Server-side search across unloaded records is not implemented.

Opening an enquiry reveals its submitted contact/travel details, itinerary proposals, private notes, follow-up tasks and public status history. Staff can add itinerary segments, write private notes, create tasks, change task status and update enquiry status. Status history is generated by the database trigger, not editable by customers or staff. The itinerary interface currently adds proposals; it does not issue reservations or update supplier inventory.

Writes require a returned record before reporting success. A failed write retains the draft for retry. A committed write followed by a refresh failure produces a distinct saved-but-refresh-failed message, so staff are not instructed to submit the same record twice. Controls remain disabled through the refresh. Profile and enquiry-status caches are updated from confirmed database responses. Paginated enquiry cache updates preserve pages and page parameters and are limited to the signed-in user’s query keys.

Email and WhatsApp delivery remain disconnected and are labelled as such. Nothing in this workflow claims to send a notification or confirm a booking.

## Additive migration and access controls

`supabase/migrations/20261018112418_customer_profile_details.sql` builds on the existing account, audit and travel CRM migrations. It adds separate name fields, Auth email and service preferences; backfills email from Auth; retains existing customer references; and generates full-UUID references for new accounts. It retains the established profile RLS policies and grants authenticated clients updates only to editable profile columns. Email, ownership, creation time and customer reference remain protected.

Auth email synchronization uses a private trigger function with an empty search path and no client execute permission. A second private trigger requires company names for new business records and changes to their category/company. Check constraints reject unsupported/duplicate/null service entries and oversized profile fields. Incomplete legacy records are preserved; name splitting and completion of missing old contact details require customer input. Application validation requires complete contact details and at least one service before saving a customer card.

Apply the new migration only after reconciling the existing remote schema and migration history. Do not replay the original broad grants over the later restrictive grants. This change does not recreate accounts, delete customer data, provision an administrator, or reset the database.
